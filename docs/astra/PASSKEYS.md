# Platform passkeys (D-49)

Astra ships a **platform authenticator**: WebAuthn credentials (passkeys) are
created and used on this device, stored in an encrypted, PIN-gated vault in the
profile. It is the Chrome-on-Linux model (Google Password Manager stores the
passkey locally) rather than the cross-device QR model; the QR design is in
[§7](#7-cross-device-qrhybrid-design-not-shipped).

The native Firefox prompt that says *"Touch your security key"* is no longer
the only answer. With passkeys on, a site that asks for a resident credential or
for user verification is served by the Astra platform token, and Astra draws the
prompt in its own surface.

## 1. What a person can do

| Surface | What works |
|---|---|
| Create a passkey | A site's *create passkey* flow creates an ES256 credential in the Astra vault and returns an `internal` transport. Sign-in then uses it with no security key. |
| Sign in with a passkey | A discoverable-credential sign-in is answered from the vault; the PIN (or system authentication) unlocks it for that one operation. |
| Settings → Privacy → Passkeys | Turn passkeys on/off for the whole browser, create the vault, set/change the PIN, enable system authentication, unlock/lock, list saved passkeys and remove one or all. |
| Private windows | Passkeys are refused before the token can act; a private window neither reads nor writes the vault. |

A hardware security key keeps working: a request that is not the passkey flow
(non-discoverable credential, cross-platform attachment) still goes to the USB
transport.

## 2. Wiring

```
Settings / sheet (ui/app)
  → bridge command `passkey_call` / `passkey_answer_prompt`
  → route table (ui/packages/bridge/src/host-transport.ts)
  → overlay/astra/host/Passkeys.sys.mjs
  → @astra/passkeys;1            (vault management, nsIAstraPasskeys)
  → astra_passkeys (Rust)        (PIN, seal, credential records)

navigator.credentials.*
  → dom/webauthn WebAuthnService → authrs_bridge
  → PlatformToken (internal transport)
  → astra_passkeys::Vault        (same file, its own unlock state)
```

The prompt path:

```
authrs_bridge status_callback → "webauthn-prompt" observer
  → Passkeys.sys.mjs (observes the same topic)
  → Host event `passkey-prompt-changed`
  → PasskeyPrompt.svelte
  → `passkey_answer_prompt` → nsIWebAuthnService.pinCallback/cancel
```

`toolkit/modules/WebAuthnPromptHelper.sys.mjs` returns early on
`webauthn-prompt` while `astra.passkeys.ui` is true, so the native doorhanger
never appears beside Astra's sheet. If the app never loads (headless chrome,
tests), the pref stays false and the native prompt remains the fallback.

## 3. Storage and cryptography

The vault is one file per profile: `<ProfD>/astra/passkeys/vault.json`
(0600, parent 0700, atomic rename on write). The optional device key for system
authentication is `<ProfD>/astra/passkeys/vault.device` (0600).

- **Credential keys**: ES256 (P-256). The private key is PKCS#8 DER generated by
  NSS through `authenticator`'s `COSEKey::generate`; only the vault sees it.
- **At rest**: the credential list is serialised and sealed with
  AES-256-CBC (NSS) plus HMAC-SHA256 over `version || IV || ciphertext`
  (encrypt-then-MAC). The tag is compared in constant time *before* any
  decryption. Subkeys are HMAC-derived from a 32-byte vault key under distinct
  labels.
- **Vault key wrapping**: the vault key is a random 32-byte key wrapped under a
  PIN-derived key (PBKDF2-HMAC-SHA256, 600,000 iterations, 16-byte salt) and,
  when enabled, under a random device key (PBKDF2, 20,000 iterations). The KDF
  uses the in-crate RFC 2104 HMAC over `sha2`; NSS's PKCS#11 HMAC imports a key
  and creates a context per call, which made the same derivation take 1.8 s.
  On this build an unlock is ~100 ms, and the seal's MAC stays on NSS.
- **PIN**: never stored. The CTAP2 client PIN protocol transmits only
  `SHA-256(PIN)[..16]` (`pinHashEnc`); that same 16-byte value is the PBKDF2
  input, so the WebAuthn path and the Settings path unlock the same vault
  without either handling the plaintext PIN twice. A wrong PIN fails the MAC,
  which is indistinguishable from a corrupt file.
- **User verification**: the token advertises `alwaysUv`, so every create and
  get requires UV. The OS verifier (`fprintd`) is tried first when enabled;
  otherwise the engine asks for the PIN. The vault is locked again when the
  transaction completes.
- **Rate limiting**: five wrong PINs lock the vault for 30 s, doubling to 5 min.
  The counter is persisted; a correct PIN is refused while locked out.
- **Isolation**: the token and the Settings service each hold their own
  `Vault`, so unlocking one never unlocks the other. A private browsing context
  is refused at the prompt seam, before the token can create or use anything.
- **No secrets in the wire**: `nsIAstraPasskeys` exposes JSON status and a
  credential list (`id`, `rp_id`, `user_name`, timestamps) only. PINs and
  private keys never cross it; the UI never receives a key.

### Threat model

| Adversary | Result |
|---|---|
| Reads profile files offline | Gets an authenticated ciphertext. The PIN must be brute-forced through PBKDF2-600k; with a 6-digit PIN that is ~10^6 derivations (~5 days on one core at ~0.4 s/derive), which is why the UI copy asks for a longer PIN and rate limits online attempts. |
| Copies `vault.device` | Device mode also needs OS authentication; the file alone does not reveal the key unless the device key path was enabled. |
| Malicious page | Sees only standard WebAuthn results. It cannot ask the vault for another RP's credential; `credentials_for_rp` filters by the RP ID the browser validated, and the allow-list/discoverable rules are enforced in the token. |
| Compromised content process | No vault access. The token runs in the parent process; the content process only gets the attestation/assertion blobs. |
| Replay of a prompt answer | Prompt answers carry the engine's transaction id; the service rejects a mismatched or finished transaction. |
| Private-window leakage | The prompt is cancelled before UV, so no credential is created and no assertion is produced. |

Known limits, stated rather than hidden:

- An attacker with code execution in the **parent** process can read the
  unlocked key while a transaction is in flight. This is the same boundary as
  every browser password store.
- `fprintd` is best-effort: no device or a failed read falls back to the PIN.
- The JS Settings service does its PBKDF2 on the main thread (~100 ms here);
  the surface paints its pending state first. Moving it to a background task
  is a follow-up; the WebAuthn path already runs off-main-thread.
- Conditional mediation (passkey autofill in a username field) is not wired;
  the modal WebAuthn flow is. A provider constant for the autofill list would
  be needed in `nsIWebAuthnService.idl`.
- PRF / hmac-secret is not advertised by the platform token yet.

## 4. Settings

The switch writes `security.webauthn.astra_passkeys` (a Rust-visible static
pref). When it is off, `GetIsUVPAA` is false, the token is not created, and
security keys remain the path. The vault path is published by the app at
startup as `astra.passkeys.vault`; an empty value also disables the token.

System authentication (`astra.passkeys.system_auth` in the vault) enables the
device-key wrap; without it every operation asks for the PIN.

## 7. Cross-device QR/hybrid design (not shipped)

The QR code in Chrome's dialog is the **CTAP2 hybrid transport** (caBLE v2):
the desktop shows a `FIDO:/…` QR that carries a one-time PSK, a tunnel server
and a tunnel id; the phone scans it, proves proximity over BLE (or connects
straight to the tunnel), and both sides open a Noise-encrypted WebSocket tunnel
over which a single CTAP2 command is exchanged. The private key never leaves
the phone.

It is not shipped in this pass, deliberately:

1. **No security-reviewed implementation.** The only maintained Rust initiator
   is `webauthn-authenticator-rs::cable`; its own module documentation says
   *"This implementation is incomplete, and has not been reviewed for
   cryptographic security"* and that the published spec omits details needed to
   interoperate. Putting an unreviewed Noise/PSK handshake in the WebAuthn path
   is the opposite of the security bar this feature is held to.
2. **It needs an external relay.** The tunnel server is Google's
   (`wss://cable.ua5v.com`) or Apple's; a browser cannot complete the flow
   without one. That is new network surface, a privacy dependency and a
   availability dependency on a third party — none of which a UI surface
   currently uses (SCOPE §"not in scope").
3. **It needs BLE.** The proximity check wants a Bluetooth adapter and, on
   Linux, `bluez`/D-Bus permission (`bluetooth` group). The QR-only variant
   still depends on the phone's OS treating the QR as a caBLE handoff.

### Staged plan, if the owner wants it

- **H1 — client skeleton (no ship).** Port the caBLE v2 initiator into
  `astra_passkeys` behind a default-off build feature, with the QR payload
  generator, tunnel connect, PSK handshake and framing covered by
  known-answer tests from the FIDO 2.2 hybrid spec. No UI yet.
- **H2 — security review.** External review of the handshake, replay window,
  cancellation/timeout, and the QR payload's confidentiality. Gate: no findings
  above low.
- **H3 — transport seam.** Add `hybrid` to the authrs bridge: when the
  request's transports include `hybrid` (or the person chooses "use a phone"),
  run the initiator and tunnel one CTAP2 command. `GetIsUVPAA` unchanged.
- **H4 — Astra UI.** A QR sheet with a countdown, "Use a phone", cancel, and a
  loud failure state. The QR is a secret: never logged, never screenshotted
  into diagnostics.
- **H5 — relay policy.** Either a first-party relay (a product/network
  decision) or an explicit, documented opt-in to a third-party tunnel; the
  setting lives beside the passkey switch and defaults off.

Nothing in H1–H5 changes the local vault: the two are independent transports
for the same credential set.
