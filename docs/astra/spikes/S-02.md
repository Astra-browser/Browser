# Spike S-02 decision: containers-vs-profile-dirs mapping for Astra spaces/profiles — U-07

Status: spike complete (P3-T05). Recommendation: **one Astra space ↔ one
Firefox contextual identity; one Astra profile ↔ one Firefox profile
directory; agent sessions ↔ ephemeral identities deleted on teardown.**

## Question

How should Astra spaces/profiles map onto Firefox isolation primitives —
contextual identities (containers) vs separate profile directories — so that
cookies/localStorage are not shared across spaces/profiles (U-07), while the
core keeps owning organisation (spaces, folders, pins, order per D-05)?

## Decision

**Ship the mapping: spaces → containers, profiles → profile directories.**

1. One Astra space ↔ one contextual identity. `Space.container_ref`
   (core + `spaces.container_ref` store column) holds the `cookieStoreId`.
   Creating a space = core `create` → host `Containers.create` → core
   `attach_container`. Deleting a space = core `remove` (returns the ref) →
   host `Containers.remove` (engine wipes that container's site data).
2. One Astra profile ↔ one Firefox profile directory
   (`profile_dir_name` → `astra-<uuid>`). Containers alone do NOT separate
   prefs, extensions, history DBs or logins — the directory boundary is what
   makes profiles strong. Containers nest inside a profile; spaces nest
   inside a profile's organisation.
3. Agent sessions ↔ ephemeral containers (`ephemeral: true`), removed with
   `forgetData: true` on teardown so run-scoped cookies/tokens vanish.
4. Tab→space binding = `Containers.bindTab`; live, new loads for the tab open
   with that container's `userContextId`. Rebinding moves the tab; removing
   a container unbinds its tabs (they fall back to the default space).
5. `Containers.update` (rename/re-theme) never touches storage — same
   `userContextId`, same partition (matches engine `update()` semantics).

Alternatives rejected: spaces-as-profiles (a profile per space would fork
prefs/extensions/history per space — heavyweight, slow to create, and breaks
the "one window, many spaces" UX); profiles-as-containers (leaks
prefs/extensions/logins across profiles — not a real profile boundary).

## Caveats recorded honestly

- **Live-browser proof not yet run**: no built binary exists in this lane,
  so isolation is proven at stub level (per-`userContextId` partitions in
  the model, mirroring the engine's per-`originAttributes` partitioning).
  The engine calls that enforce the same property live
  (`deleteDataFromOriginAttributesPattern`, tab `usercontextid` binding) are
  verified in source but not executed. Follow-up once the P3 binary exists:
  red-cookie-in-A / read-in-B live probe via geckodriver (set cookie +
  localStorage in space A, assert absent in space B, delete space A, assert
  wiped) — same scenario the stub test encodes.
- **IME/devtools-style per-container UI**: out of scope — containers need no
  per-pane chrome beyond the existing tab strip badge work.
- **Tab→container live wiring** (`Content`/`Tabs.create` accepting a
  `cookieStoreId` and passing `userContextId` to `addTab`/`loadTabs`) belongs
  to the spaces UI phase that consumes this spike, not to this spike.
- **No reschema**: P2-T04 `spaces.container_ref` / `profiles` tables reused
  as-is; core persists the mapping through the existing store + session
  snapshot path.
